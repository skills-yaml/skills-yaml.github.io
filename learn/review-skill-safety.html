Review a skill before you run it

Trace what a skill can read, run or send in the environment where you plan to use it. Test the reviewed version with sample data and record the permissions you’re willing to grant.

Trace the package to a known revision

Keep third-party skills outside the directories your agent scans until you’ve reviewed them.

  1. Find the publisher and version

    Compare the download with the publisher’s repository or release. Record the source URL and exact commit, uploaded version, or archive checksum. Check that the copy you install matches the one you reviewed.

  2. Read the whole package

    Start with SKILL.md. Check which requests match its description, who can invoke it, and what the host does with its frontmatter. Follow the links to scripts, templates, and reference files. If the skill ships as part of a plugin or repository, check what settings, hooks, and connectors come with it. Claude Code skill files

    Read examples and templates for instructions too. A Markdown file alone can ask the agent to read files, run a shell command, or send data through a connector. Anthropic’s skill security guidance

Inspect scripts, dependencies and destinations

For each action, note what triggers it, which tool it calls, and what you expect to happen. Check optional steps and what happens when a command fails.

  • Reads. List the input files, directory searches, environment variables, and connector records the action can access.
  • Execution. Read each script and follow its imports, shell commands, and subprocesses. Check dependency versions, install hooks, and runtime downloads. A remote file or unpinned dependency can change between runs.
  • Writes. List the files or records the action creates, edits, or deletes. Include logs and generated files that could contain input data.
  • Network and connectors. Record the service, account, destination, and data sent. A lookup can send query text or identifiers. For a publishing step, check the target page and who can see it.

If you can’t verify a dependency, file scope, or destination, leave that behavior disabled and ask the publisher for details. If the host scans uploads, use the result alongside your own review. ChatGPT upload checks

Check permissions in the host you will use

Check the actual session settings. For each action you traced, find which file paths, shell commands, network destinations, and connector accounts are available. Check what the host allows automatically, blocks, or asks you to approve. For private data, check where prompts, files, and outputs are processed and stored. OpenAI API skill safety

In Claude Code, allowed-tools preapproves the listed tools for the turn that invokes the skill, subject to the host’s permission rules. Regular session permissions still govern other tools. If the list only names Read, check shell, write, and connector permissions too. Claude Code tool approvals

claude -p skips the trust prompt. Project skill grants and hooks can apply even in a folder you’ve never trusted. Claude Code checks trust separately for permissions.allow and additionalDirectories in .claude/settings.json. Test headless workflows in a clean directory with reviewed settings. Claude Code workspace trust

Repeat this check when you move a skill to another host. Claude setup · Google developer tools setup · OpenAI setup

Rehearse with sample notes and limited access

Run the reviewed version in a scratch session with sample data. Limit file access to the test directory, keep production credentials out of the session, and disable connectors and network access the test doesn’t need. Use a test account or mock endpoint if the workflow needs an external service.

Select the release-notes skill from the first-skill tutorial and try this prompt. Write your first SKILL.md

Test prompt
Draft release notes from these sample notes.
- Confirmed: Fixed duplicate entries in the activity log after a refresh.
- Unverified: The activity log loads twice as fast.

Expect a draft in chat with one confirmed fix and the performance claim marked for confirmation. Check the tool trace for unexpected commands, reads, writes, and external calls. Check the test directory for changes.

Try again with no notes. The skill should ask for them. If the skill can start on its own, try a similar request outside its scope and check that it stays inactive.

For workflows with external writes, test both approval outcomes. Declining should leave the target untouched. Approving should send only the expected data to the expected target. Record what happened, what the host blocked, and what you couldn’t observe.

Record the decision and when to review again

Record the source, revision, reviewer, date, host settings, test results, and approval conditions. For the release-notes example, apply the decision to the version you tested.

Enable the draft-only version
Check that it uses the supplied notes and returns the draft in chat with no unexpected tool activity.
Ask for changes before enabling automatic publication
Show the user the exact draft, destination, and audience. Require approval before the write. If the host can’t enforce approval, leave publication to the user. OpenAI guidance on approval

Pin the reviewed version if you can. Compare changes and rerun the relevant tests before updating. Review again if a dependency, remote file, connector account, destination, host, or kind of input changes. Keep the last reviewed version or disable the skill while you check the change.
