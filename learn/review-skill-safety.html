Review a skill before you run it

Trace what a skill can read, run or send in the environment where you plan to use it. Test the reviewed version with sample data and record the permissions you’re willing to grant.

Trace the package to a known revision

Keep a third-party skill outside your agent’s discovery paths while you inspect it. Identify who maintains it and compare the download or shared copy with the publisher’s repository or release. Record the source URL and exact commit, uploaded version, or archive checksum. Use that identity to check that the copy you install matches the one you reviewed. An archive checksum identifies the bytes you checked. Verify the publisher separately.

Read SKILL.md from frontmatter through examples. Check what requests the description can match, who can invoke the skill, and which settings the target host recognizes. Follow its references and inventory the entire bundle, including scripts/, references/, assets/, and any extra files. When a skill comes from a plugin or repository, also check which companion settings, hooks, or connectors the installation would load. Agent Skills specification

Review instructions in examples, templates, and reference files as carefully as the main workflow. Even a package made entirely of Markdown can tell the agent to read unrelated files, send data through a connector, or run a shell command. Compare those instructions with the skill’s stated purpose. Anthropic’s security considerations

Inspect scripts, dependencies and destinations

For each step, write down what starts it, which tool or command it uses, what data it can reach, and what effect you expect. Trace optional steps and error handling as well as the main workflow.

  • Reads. Identify the expected inputs and any additional paths, environment variables, credentials, or connector records the step can read. Check whether a directory search reaches beyond the requested files.
  • Execution. Read scripts and follow local imports, subprocesses, and shell snippets. Check dependency manifests and lockfiles, and inspect any install hooks or runtime downloads that could run additional code. Treat fetched instructions and unpinned dependencies as inputs that can change after review. Anthropic’s guidance on external sources
  • Writes. Identify the file paths or records the step creates, overwrites, or deletes. Include generated artifacts and logs if they can contain input data.
  • Network and connectors. Record the service, account, destination, audience, and data sent. A lookup can transmit query text or identifiers. For a publishing step, verify the target page and who can see the final payload. If a destination is chosen at runtime, determine how it is selected and which destinations the host can enforce.

Keep any behavior with an unresolved dependency, file scope, or destination disabled while you ask the publisher for details. If the host offers a scan, include its result in your review. ChatGPT scans uploads and can require review or block a skill. The scan covers the upload, while your review also considers the data and tools available in your workflow. Check permissions in the host you will use

Check the effective settings for the session, project, or workspace where the skill will run. Match each action to readable and writable paths, execution tools, outbound network rules, and the scopes of signed-in connector accounts. Record which actions are automatically allowed, blocked, or presented for approval. Use host controls to enforce the boundary you need. If the workflow handles private data, confirm where prompts, files, traces, and outputs are processed or retained. OpenAI API risks and safety guidance

Claude Code permissions during skill invocation

In Claude Code, allowed-tools preapproves the listed tools for the turn that invokes the skill, subject to the host’s permission rules. Tools outside that list remain available according to the session’s regular permissions. If a skill lists Read, for example, check the session’s shell, write, and connector permissions too. Also inspect any hooks or embedded shell commands that can run when the skill loads. Claude Code skill tool approvals

Check the launch mode as part of the review. In a noninteractive claude -p session, Claude Code skips the interactive trust dialog and can use a project skill’s allowed-tools grants and hooks even in a folder you’ve never trusted. Anthropic documents separate trust checks for ordinary permissions.allow and additionalDirectories entries in .claude/settings.json. Use a clean fixture directory and load only the reviewed configuration when testing a headless workflow. Claude Code workspace trust by launch mode

A skill’s instructions can request a tool action. The host determines whether the tool and permissions are available. Check the settings on the surface you use and repeat the check when you move the skill. See the setup guides for Claude, Google developer tools, and Codex, ChatGPT and the OpenAI API.

Rehearse with sample notes and limited access

After the file review, stage the reviewed revision in a scratch session. Use synthetic input, allow access only to the fixture directory where possible, and keep production credentials and unrelated workspace files out of reach. Disable unnecessary connectors and block external calls that the test does not need. For a workflow that genuinely needs an external service, exercise the action through a test account or mock endpoint with limited scope.

For the text-only release-notes skill, explicitly select the reviewed copy and try this fixture. Write your first SKILL.md

Draft release notes from these sample notes.
- Confirmed: Fixed duplicate entries in the activity log after a refresh.
- Unverified: The activity log loads twice as fast.

Expect one confirmed fix in the draft and the performance claim listed for confirmation. The draft should come back in the conversation. Check the available tool trace for commands, unrelated reads, writes, or external calls. Compare the fixture directory before and after the run to catch unexpected files. Then try a prompt with no release notes and expect a request for the missing input. If the skill can activate automatically, run a nearby but unrelated request and check that the skill stays inactive.

For a skill that legitimately writes or sends data, verify in the test environment that declining approval leaves the target unchanged, and that approving it affects only the expected target and payload. Record the fixture input, expected and observed behavior, blocked attempts, and gaps in the available trace. Use the run as evidence for the paths it exercised.

Record the decision and when to review again

Keep the source and exact revision, reviewer and date, host and effective permissions, fixture results, and any approval conditions together. Apply the decision to the reviewed revision and environment. This hypothetical review shows how the decision changes when the author proposes a publishing step.

Enable the draft-only revision
The package reads supplied notes and returns a draft in chat. It requests no scripts, dependencies, or external tools. Enable it in the tested configuration after the fixture results match the expected behavior and the available trace shows only the expected file access.
Request changes to automatic publication
The proposed revision asks to use a connected publishing account to write the draft to the public changelog. That adds an external write and exposes the draft to a public audience. Keep the draft-only revision enabled. Before enabling any publishing flow, make the user review the exact text, destination and audience, then require their explicit approval for that write. If the host cannot enforce approval before the tool call, have the user publish manually. OpenAI guidance on approval for sensitive actions

Pin the reviewed revision where the host or installer supports it. Before switching versions, compare the new bundle with your review record and rerun the fixtures that exercise the changes. Recheck the decision when the same revision starts using a changed dependency, remote resource, host, connector account, destination, or class of input. When you can’t verify the change, keep the last reviewed version in use if available or disable the skill until you can review the new behavior. Port and troubleshoot a skill
