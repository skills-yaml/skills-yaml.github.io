Evaluate and improve a skill

Find out whether your release-notes skill handles the right requests and produces drafts that hold up to review. Run the same cases against a baseline before releasing a revision.

Define what a good run looks like

Start with the workflow from Write your first SKILL.md. The release-notes skill turns supplied change notes into a user-facing draft. It groups confirmed changes, flags uncertainty, asks for missing notes, and returns the draft in the conversation.

  • Discovery. Check whether the host makes the intended skill and version available to the agent. Use the host’s skill list or configuration where available.
  • Activation. Check whether a request causes the host to select or load that skill. Set an expected outcome for each prompt.
  • Output quality. Check what the agent says and does against the supplied notes and the workflow’s requirements. A model can produce a passing draft without loading the skill.

Build cases from requests you see in practice. Pull out the change notes, the request as the user phrased it, and what an editor had to correct. Use sanitized inputs and include cases that prompted edits, such as an unverified performance claim. Write down what an evaluator should see in the draft and what the host should show about skill use. Agent Skills guidance on designing output tests

Describe when the skill should activate

A description such as “Helps with releases” could match requests about drafting, deployment, or publishing. Name the user’s intent and the material they bring. The following candidate adds natural wording for a request that the original description may miss. For an experiment, change only the description field in SKILL.md so the instructions stay the same across variants.

description: >-
  Use when the user wants a draft of release notes, a changelog entry,
  or a customer-facing what's-new summary based on supplied change notes,
  or asks to draft one before supplying the notes. Return a draft for review.
  Deployment, publishing, and release scheduling are outside the workflow.

Under the specification's progressive disclosure model, the agent sees the name and description during discovery and loads the body on activation. Test relevant and closely related out-of-scope requests to see where your description draws the line. Agent Skills specification on progressive disclosure · Optimizing skill descriptions

Build an activation test set

Use these proposed tests as a starting point. Replace [notes] with all three lines of the fixture. Send each prompt as written in a fresh session with the skill available so the host selects automatically. Include requests that share the same vocabulary and source material but ask for different work. Agent Skills guidance on activation cases · Anthropic’s guide to testing skills

Confirmed feature: Added CSV export to the activity log.
Confirmed fix: Corrected the time zone shown on scheduled reports.
Unverified claim: CSV export runs twice as fast.
Proposed release-notes tests
Case Prompt Expected activation Output checks
Direct request Draft release notes from these changes for customer review. [notes] Yes Puts the feature under Added and the fix under Fixed. Flags the speed claim under Needs confirmation.
Paraphrase Turn this list into a short “what changed” update I can send to users after review. [notes] Yes Includes CSV export and the time-zone fix. Keeps the speed claim in Needs confirmation.
Missing input Write a customer-facing changelog entry for our next release. Yes Asks for change notes. Produces zero fabricated release items.
Unsupported claim Draft customer release notes from “Confirmed feature: Added CSV export.” Include that exports run twice as fast, which we haven't measured yet. Yes Includes CSV export in the draft. Keeps the speed claim in Needs confirmation.
Deployment planning Give me a pre-deployment checklist for a release that adds CSV export. No Returns checklist items for deployment preparation.
Internal review Identify what QA should verify before shipping these changes. Give me a test checklist. [notes] No Addresses the test checklist request.
Publishing request Where do I publish the release notes I already wrote? No Answers the publishing question or asks where the project publishes.

Record the observed skill name and relevant event from host activity, a trace, or a log. Mark activation observed when the host shows selection or loading, absent when a complete record of those events shows none, and unknown when visibility is incomplete. An agent’s claim that it used the skill is insufficient evidence. For a miss, verify discovery, check whether automatic selection is enabled, then try explicit invocation as a diagnostic. Exclude that run from automatic-selection counts. Agent Skills guidance on measuring activation

Score the draft and inspect the run

Automate checks the workflow defines exactly. For the direct case, normalize Markdown heading markers and whitespace, then check for the title Release notes draft, the headings Added and Fixed, and verify that the reply omits Changed. For missing notes, check that the reply has no draft heading, then read it to confirm that it asks for the notes and invents no changes. Inspect tool activity for publication or sending attempts. Mark that check unknown if the host gives you incomplete activity data.

Use a rubric for properties that can survive changes in wording. Score each applicable criterion pass or fail and save the relevant line from the reply or trace.

  • Coverage. The draft covers both confirmed changes and identifies the activity log and scheduled reports correctly.
  • Factual accuracy. Every statement of fact follows from the notes. The draft adds no unsupported release date, version, or benefit.
  • Treatment of uncertainty. The speed claim appears only under Needs confirmation, with a clear request to verify it.
  • Readability. A customer can tell what changed from short, concrete bullets that preserve the scope of each change.

Apply the same checks and rubric across variants. If a model grades the rubric, give it the input notes and check its judgments against examples reviewed by a person. Read failed trials to distinguish a workflow error from a bad check. Agent Skills guidance on grading outputs · OpenAI evaluation best practices · Anthropic’s guide to agent evaluations

Compare runs under recorded settings

  1. Compare the current and candidate versions under the same skill name, with one version available per run. For output quality, include a baseline with only release-notes disabled. Use the same ordinary prompt in each condition.
  2. Record the host and version, model identifier, exposed reasoning or sampling settings, enabled tools and skills, working directory, project instructions, and skill version or commit. Save the exact prompt and fixture with each trial.
  3. Choose a trial count before running, such as three attempts per case and variant for a first pass. Start a fresh session each time and reset any data or files a previous run could have changed. Save the activation evidence, full reply, and grades.
  4. Test with the rest of the usual skills enabled. For example, if the host has a deployment skill, use the deployment-planning case to check that release-notes stays inactive. If a release-related skill loads on a drafting request, record which skills loaded and check whether their instructions interfered. Repeat the ambiguous cases with release-notes alone to diagnose interference.
  5. For each enabled variant, count misses on expected positives and unwanted activations on expected negatives. Report unknowns alongside those counts and include the total trials in each group. Compare output pass counts across all variants, including the disabled baseline. Review individual failures alongside any totals.

Before tuning, set aside realistic in-scope and closely related out-of-scope prompts for the final comparison. Use the remaining prompts to edit the description. If a held-out case becomes part of tuning, add a fresh held-out case before the next comparison. Agent Skills guidance on testing revised descriptions · Agent Skills guidance on baseline comparisons

Revise the smallest part and rerun before release

Use the evidence to identify where to make the change. If the host cannot discover the skill, check installation and configuration. If it discovers the skill and repeated runs miss a relevant request, check automatic invocation settings and revise the description where it leaves the request ambiguous. If the skill loads and the draft states the speed claim as fact, strengthen the instruction that moves unverified claims into Needs confirmation. If you change a linked resource, rerun a case that needs it and inspect the trace for the resource read. Agent Skills specification on loading supporting resources

Decide what counts as a release pass before looking at the results. For this example, require every repeated trial to pass the missing-input and unsupported-claim checks. Require the targeted cases to improve and inspect any new wrong activations, missed selections, or failed output checks before approving. Run the full suite again with the held-out prompts. If you support multiple hosts, repeat the fixture on each host.

For each regression, save a case ID, the exact prompt and notes, the expected result, the observed activation and output with evidence, and the settings and versions used. Add the case to the repeatable suite and record the release decision with the per-case counts. Once the candidate passes, follow the registry guide to update an existing skill package.
