Port and troubleshoot a skill

Run the same release-notes skill in Claude Code, Codex, and Gemini CLI. Use one set of change notes to find where discovery, activation, or execution starts to differ.

Identify what travels with the skill

Start with the release-notes skill you authored. Copy the whole release-notes/ folder. Keep the SKILL.md frontmatter (name and description), the Markdown workflow, and any bundled files together. Use the skill name for the folder and preserve relative paths like references/style-guide.md. GitHub Copilot also uses this folder format and can discover project skills in .agents/skills/. GitHub Copilot skill structure and locations

Check which settings the destination reads. Claude Code uses disable-model-invocation: true in frontmatter to restrict automatic selection. Codex uses policy.allow_implicit_invocation: false in agents/openai.yaml. Claude Code invocation settings · Codex invocation policy

Check the destination’s runtime and permissions before running an adapted skill that needs a script or connector. Document required executables, libraries, and network access in the skill. For example, the Claude API uses a code execution container with preconfigured dependencies and no network access. The release-notes example needs only the supplied text. Claude API skill runtime

Install release-notes in each host

Use the same reviewed folder in each local CLI and start the sessions at the project root. Copy or update the folder directly under the discovery directory, so SKILL.md sits one level below it.

Claude Code

Place the folder at .claude/skills/release-notes/. Check /skills and run /reload-skills if a new copy is missing. Invoke /release-notes with the test prompt and changes below. If another copy shares the name, check user and enterprise installs. Enterprise skills take precedence over personal skills, which take precedence over project skills. Plugin commands use a namespace. Claude Code skill discovery and invocation

Codex CLI

Place the folder at .agents/skills/release-notes/. Check /skills or type $release-notes and select the skill before adding the test prompt. Restart Codex if the copy fails to appear. Codex scans .agents/skills/ from the working directory up to the repository root, and multiple entries with the same name can appear in its selectors. Check the path of the copy you select. Codex skill discovery and invocation

Gemini CLI

Gemini CLI can use the same workspace .agents/skills/release-notes/ copy. Run /skills reload after adding it and check /skills list. For a named test, ask Gemini to use release-notes and watch for activate_skill. Approve activation after checking the directory shown in the prompt. Workspace skills take precedence over user, extension, and built-in skills, in that order. Within the workspace or user tier, the .agents/skills/ alias wins over .gemini/skills/. Gemini CLI skill discovery and activation

For other surfaces and install methods, see the host guides. Claude · Google developer tools · Codex, ChatGPT, and the OpenAI API

Find the first failing stage

Find the first stage that failed. The host presents skill descriptions to the model, loads the instructions on activation, and reads supporting files when the workflow needs them. Gemini CLI skill lifecycle

StageWhat to checkNext action
Discovery Look for the intended copy in the host’s list. Check the working directory, install scope, uppercase SKILL.md, valid frontmatter, and whether the skill is enabled. Validate the source folder, refresh the list, and check for copies with the same name in other scopes before editing the draft workflow.
Activation Try the named invocation first. If it loads and the ordinary prompt misses, check whether automatic invocation is enabled and whether the description fits the request. In Gemini CLI, check whether activation is awaiting approval. Resolve the host setting or consent prompt. If the skill is available for automatic selection, put the primary use case early in the description and retry a matching prompt and a near miss.
Resources and execution After activation, look for a missing file, permission denial, unavailable tool, or runtime error. Check the exact relative path from the skill folder, the session’s filesystem access, and any interpreter, library, or connector used by the workflow. Restore missing files or correct their paths. For a documented dependency or permission, use the destination’s supported configuration and retry the failing step.
Output Once the intended instructions and required resources loaded, compare the draft with the supplied changes and the skill’s drafting rules. Clarify the rule the draft missed, such as placing an unverified claim under Needs confirmation. Rerun the same fixture to check the change.

Codex catalog budget. A skill can exist on disk while missing from the model’s initial catalog. By default the catalog uses at most 2% of the model’s context window, with an 8,000-character fallback when that window is unknown. Codex shortens descriptions first and may omit entries and show a warning in large skill sets. If named selection works but automatic matching still misses, retry with fewer skills enabled or inspect skills.max_context_tokens. The budget applies to the initial list. Codex reads the full instructions for a selected skill. OpenAI guidance on the Codex catalog budget

Repeat the same fixture on each host

In a fresh session, use the host’s named invocation above and submit the prompt below. In a second fresh session, send the same prompt without naming or selecting the skill. Keep the installed copy, input, and model settings the same for both runs on that host. Record whether the intended copy loaded using the host’s available activation evidence, such as Gemini CLI’s activation prompt. A passing draft can also come from the model on its own. Evaluate and improve a skill

Release-notes test prompt
Draft release notes from these change notes.

- Confirmed: The activity log now offers CSV export.
- Confirmed: Fixed duplicate entries in the activity log after a refresh.
- Unverified: CSV export may be twice as fast as the previous internal prototype.

Check for CSV export under Added, the duplicate-entry fix under Fixed, and the speed claim only under Needs confirmation. The draft should stay in the conversation. Record the host and version, model, skill source path, invocation method, evidence of activation, and which checks passed. After making a change, repeat the failing run with the same notes.

Share the verified package

When you publish through skills-yaml, use metadata.skm-version to mark the package release and metadata.skm-dependencies if the package depends on other registry skills. A consumer’s skills.yaml declares packages and version pins for skm. The skill’s portable instructions and resources still live inside its folder. Registry package structure

Follow the registry packaging and publishing guide to share the tested folder. Then install the published version in a clean project and repeat the fixture on your supported hosts.
