What a package is

A skill is a directory with a SKILL.md: instructions an agent loads when a task matches, plus any references, templates or scripts it needs.

A registry package is that skill made installable and versioned. It adds three things a plain skill does not have: an exact version directory, two alias symlinks, and a second copy of the latest payload at the package root. Most rejected contributions get one of those three wrong, so the steps below build them in order.

The rules come from the registry's SKILL_STRUCTURE.md, VERSIONING.md and its validator. Where this guide and those disagree, they win.

1. Write SKILL.md

Frontmatter first. Keep it to three fields:

---
name: release-notes
description: Draft release notes from merged pull requests. Use when preparing a release, summarizing changes since the last tag, or writing a changelog entry.
metadata:
  skm-version: "0.1.0"
---
name
Equal to the directory name. Lowercase letters, digits and single hyphens, 1–64 characters, with no hyphen at the start or end.
description
Most agents read only this before deciding whether to load the skill, so say what it does and when to use it. At most 1024 characters.
metadata.skm-version
The package version, as a quoted string. Everything under metadata must be a string.

The body is instructions for an agent that is about to act, not documentation for someone browsing. Start with what to do. Move long reference material into references/ and link it, so the agent loads it only when it needs it.

Stay inside the portable subset

One SKILL.md is installed into many agents, and their rules conflict. Following the strictest rule on each point gives you a file that works everywhere:

RuleStrictest agents
name requiredCodex, Cursor, Copilot, OpenCode, Kilo Code
name equals directoryOpenCode
name ≤ 64, kebab-caseOpenCode, Copilot
description requiredCodex, Cursor, Copilot, OpenCode, Antigravity
description ≤ 1024Roo Code, Kilo Code

Leave out agent-specific fields such as allowed-tools, paths, icon, model or disable-model-invocation. They work only in the agent that defines them. If a skill needs one, it isn't portable, and it belongs in your own project rather than a shared registry.

2. Build the layout

skills/<namespace>/release-notes/
├── SKILL.md            # identical to v0.1.0/SKILL.md
├── references/         # identical to v0.1.0/references/
├── latest -> v0.1.0
├── default -> v0.1.0
└── v0.1.0/
    ├── SKILL.md
    └── references/
        └── style.md

Build the version directory first, then copy its whole payload to the root. The validator compares the two byte for byte, including file permissions, so copy the files rather than retyping them:

cd skills/<namespace>/release-notes
cp -a v0.1.0/SKILL.md v0.1.0/references .
ln -s v0.1.0 latest
ln -s v0.1.0 default
  • Links must work from both copies. Skills get installed from the root and from the version directory, so every relative link has to resolve in both places. The usual mistake is copying SKILL.md to the root but not the references/ directory it links to.
  • Aliases are relative and stay inside the package. Each alias target is a single path segment like v0.1.0, with no slashes and no ... latest must point to the highest version.
  • Scripts need the executable bit in both copies. cp -a keeps it.
  • Limits: at most 256 files and 10 MB per package, and no symlinks inside a version directory.

3. Declare dependencies

Use a dependency only when your skill can't work without another one:

metadata:
  skm-version: "0.1.0"
  skm-dependencies: "workspace/write-spec@0.2.0, workspace/review-changes@0.2.0"

Each entry is an exact version from the same registry. Separate entries with a comma and one space, don't repeat any, and make sure no chain of dependencies loops back on itself. Version ranges, aliases and paths are rejected.

Don't use a dependency to group skills that are merely useful together. That is a bundle — see section 7.

4. Validate

Run the registry's gates before you open a pull request:

task check    # structure, aliases, payloads, frontmatter, dependencies, immutability
task test     # the validator's own test suite

If a check fails, the error message names the rule it broke. Search validate_registry.py for that message to see exactly what it checks.

The gates confirm that a package is well formed. They can't tell whether it's safe. Before you trust a skill, especially one with scripts, read what it actually tells the agent to do. The skills-yaml/skill-reviewer skill gives you a structured way to do that; it will be installable once the registry's next release reaches main.

5. Publish and version

Add the skill to the registry README's catalog, then open a pull request against develop. Merging into develop integrates the skill; it becomes installable only when develop is released into main, which is what skm resolves against.

  • Published versions are immutable. Once a version directory reaches main, its files, permissions and bytes are frozen. You can't edit it or delete it.
  • To change a skill, publish a new version. Add a new version directory, point latest at it, update the root payload, and leave the old directory in place for anyone pinned to it.
  • Choose the version number by what changed for users. If the skill now tells an agent to do something different, that's at least a minor release.
  • To take a version down, withdraw it. Delete its directory and record it in WITHDRAWN.yaml with a date and a reason. This doesn't remove it from Git history, so treat anything it contained as already public.

6. Where it lands

A user adds your skill by name, and skm links it into each configured agent's skill directory:

skm add <namespace>/release-notes --source default
skm install

skm 0.6.0 supports sixteen agents. Several read the shared .agents/skills directory, and skm creates one link there for all of them rather than one per agent.

Two cases where installing isn't enough on its own: Pi loads project skills only after you trust the project, and Hermes has no project directory at all, so it only picks up skills installed with --global.

7. Bundle skills

Not available yet. The registry doesn't yet accept bundles outside the workspace namespace, and skm bundle add isn't in skm 0.6.0. This section describes the agreed contract so you can plan for it. skm's search already shows any bundles a registry publishes.

A bundle is a name for a set of skills that are offered together. It is not a skill, and it is not a dependency:

Dependency
"This skill needs that one to work." It's declared inside a skill, and skm always installs it along with that skill.
Bundle
"These skills are useful together." It's declared in the namespace manifest, and a user chooses to add it.

Don't build a bundle as an empty skill that lists its members as dependencies. Every agent would still index it and show it as something you can run, and it misdescribes how the skills relate to each other.

Declare it in the namespace manifest

A bundle lives in skills/<namespace>/manifest.yaml:

schema_version: 2
namespace: skills-yaml
packages:
  skill-creator: "0.1.0"
  skill-reviewer: "0.1.0"
bundles:
  authoring-toolkit:
    packages:
      - skill-creator
      - skill-reviewer
  • namespace must match the name of the directory the manifest is in.
  • packages must list exactly the current version of every package in the namespace. That keeps a bundle from pointing at versions that aren't published.
  • Every bundle member must also appear in packages, listed once, in a fixed order.
  • Bundle names follow the same rules as skill names.
  • Membership is always written out. skm never works it out from the directories.
  • The manifest is optional, but it's not allowed in a namespace that has no packages.

The workspace namespace needs a few more fields, which record the source repository and revision its skills were generated from. Namespaces you write by hand, like the example above, need only the fields shown.

How users will install it

skm bundle add skills-yaml/authoring-toolkit --source default --dry-run
skm bundle add skills-yaml/authoring-toolkit --source default --yes

Adding a bundle writes each of its skills into skills.yaml as its own entry, pinned to an exact version. After that, the entries behave like any other: skm install, skm check and version changes work as usual. skm doesn't remember that the entries came from a bundle, and it won't update them automatically if the bundle's membership changes later.
