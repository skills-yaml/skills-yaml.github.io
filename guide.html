Authoring guide

This guide explains how to write a skill that works in every agent skm supports, and how to offer several skills together as a bundle.

What a package is

A skill is a folder that contains a file called SKILL.md. That file holds the instructions an agent follows when a task calls for the skill, and the folder can also hold reference documents, templates or scripts that the instructions point to.

To share a skill through a registry, you turn it into a package. A package contains the same skill, but it is versioned. Each release lives in its own folder named after its version number, two small links called latest and default point to the releases you want people to use, and a copy of the latest release sits at the top of the package so that tools can find it easily. The sections below explain each of these parts.

This guide summarises the registry's rules. The official source is the registry itself: its SKILL_STRUCTURE.md and VERSIONING.md files, together with its validation script. If this guide and those files ever disagree, please follow the registry.

1. Write the SKILL.md file

Every SKILL.md starts with a short header, called frontmatter, which is written in YAML between two lines of three dashes. A skill published in a registry needs only three fields in it:

---
name: release-notes
description: Draft release notes from merged pull requests. Use when preparing a release, summarizing changes since the last tag, or writing a changelog entry.
metadata:
  skm-version: "0.1.0"
---
name
The name must be exactly the same as the name of the skill's folder. It can contain lowercase letters, digits and single hyphens, it can be at most 64 characters long, and it cannot start or end with a hyphen.
description
Most agents read only the description when they decide whether a skill is relevant, so it should say both what the skill does and when it should be used. It can be up to 1,024 characters long.
metadata.skm-version
This is the version number of the package. Write it in quotes, because every value under metadata must be text.

The body of the skill comes after the frontmatter. Write it for an agent that is about to carry out the task, and start with the steps it should take. If the skill needs long background material, put it in a references folder and link to it from the body, so that the agent opens those files only when it needs them.

Make the file work in every agent

Your SKILL.md will be installed into many different agents, and they do not all apply the same rules. If you follow the strictest version of each rule, the same file will work in all of them. The table below shows which agents set each limit.

RuleAgents that require it
A name is presentCodex, Cursor, Copilot, OpenCode, Kilo Code
The name matches the folder nameOpenCode
The name has at most 64 charactersOpenCode, Copilot
A description is presentCodex, Cursor, Copilot, OpenCode, Antigravity
The description has at most 1,024 charactersRoo Code, Kilo Code

You should also avoid fields that only one agent understands, such as allowed-tools, paths, icon, model or disable-model-invocation. Other agents usually ignore these fields, which means the skill will not behave the same way everywhere. If your skill really depends on one of them, it is better to keep it in your own project than to publish it in a shared registry.

2. Set up the package

A finished package looks like this:

skills/<namespace>/release-notes/
├── SKILL.md            # the same file as v0.1.0/SKILL.md
├── references/         # the same folder as v0.1.0/references/
├── latest -> v0.1.0
├── default -> v0.1.0
└── v0.1.0/
    ├── SKILL.md
    └── references/
        └── style.md

The easiest way to build it is to create the version folder first, with the SKILL.md file and everything else inside it, and then copy the contents of that folder to the top level of the package. The registry checks that the two copies are identical, including their file permissions, so it is safer to copy the files than to write them twice. Once the copy is in place, create the two links:

cd skills/<namespace>/release-notes
cp -a v0.1.0/SKILL.md v0.1.0/references .
ln -s v0.1.0 latest
ln -s v0.1.0 default

A few details are worth checking before you move on:

  • People can install the skill from either copy, so every link inside SKILL.md has to work from both places. In practice, this means copying the whole references folder to the top level, not only the SKILL.md file.
  • The latest and default links must point to a version folder inside the same package, using just its name, such as v0.1.0. The latest link must always point to the highest version you have published.
  • If the skill includes scripts, they must be executable in both copies. The cp -a command keeps these permissions for you.
  • A package can contain at most 256 files and 10 MB of data, and a version folder cannot contain any symbolic links of its own.

3. Declare dependencies

If your skill cannot work without another skill, you can declare that skill as a dependency, and skm will install it automatically:

metadata:
  skm-version: "0.1.0"
  skm-dependencies: "workspace/write-spec@0.2.0, workspace/review-changes@0.2.0"

Each dependency must name an exact version of a skill from the same registry. Separate the entries with a comma followed by a space, and list each one only once. Also make sure that no chain of dependencies leads back to the skill it started from. Version ranges, aliases such as latest, and file paths are not accepted.

Dependencies are not the right tool for grouping skills that simply work well together. For that purpose, use a bundle, which is described in section 7.

4. Check your package

Before you open a pull request, run the registry's checks from the root of the repository:

task check    # checks the structure, links, frontmatter, dependencies and versions
task test     # runs the tests for the checks themselves

If a check fails, its error message tells you which rule was broken. You can search for that message in validate_registry.py to see exactly what the check looks for.

These checks confirm that a package is put together correctly, but they cannot tell you whether it is safe to use. Before you trust a skill, and especially one that includes scripts, read what it actually asks the agent to do. The skills-yaml/skill-reviewer skill can guide you through that review, and you can install it with skm add skills-yaml/skill-reviewer --source default.

5. Publish and update it

When the package is ready, add it to the list of skills in the registry's README and open a pull request against the develop branch. Merging into develop brings your skill into the registry, but people can install it only after develop has been released into main, because main is the branch that skm reads from.

Once a version has been released to main, it can no longer be changed or removed. This protects everyone who has pinned that version in their projects. If you need to change the skill, publish a new version instead: add a new version folder, point latest to it, update the copy at the top of the package, and leave the old folder where it is.

Choose the new version number according to what has changed for the people who use the skill. If the skill now asks the agent to do something different, the change deserves at least a new minor version.

In the rare case where a published version has to be taken down, for example because it exposed private information, you can withdraw it. To do this, delete its folder and add an entry to WITHDRAWN.yaml that records the date and the reason. Keep in mind that the version still exists in the repository's Git history, so you should treat anything it contained as public.

6. Where the skill is installed

People add your skill to their project by name, and skm then links it into the skill folder of each agent they use:

skm add <namespace>/release-notes --source default
skm install

skm 0.7.0 supports sixteen agents. Several of them read from the same shared folder, .agents/skills, and in that case skm creates a single link that all of them can use.

In two situations, installing a skill is not quite enough. Pi loads a project's skills only after you have marked the project as trusted. Hermes does not read project folders at all, so it only finds skills that were installed for your user account with the --global option.

7. Bundle skills together

A bundle is a named group of skills that are meant to be used together. It is different from a skill, because it contains no instructions of its own. It is also different from a dependency, because the skills in a bundle do not need each other in order to work.

Dependency
A dependency means that one skill needs another one in order to work. It is declared inside the skill, and skm always installs the two together.
Bundle
A bundle means that several skills are useful together. It is declared in the namespace manifest, and people choose whether they want to add it.

It can be tempting to create a bundle as an empty skill that lists the other skills as its dependencies, but please avoid this. Every agent would still show the empty skill as something it can run, and it would describe a relationship between the skills that does not really exist.

Declare the bundle in the namespace manifest

A bundle is declared in a file called manifest.yaml at the top of the namespace folder. If you maintain the namespace by hand, you only write the bundles section yourself. For example, to offer the two authoring skills together, you would create skills/skills-yaml/manifest.yaml with this content:

bundles:
  authoring-toolkit:
    packages:
      - skill-creator
      - skill-reviewer

Then run this command from the root of the registry:

task manifest

The command reads the package folders and completes the file for you. It adds the name of the namespace and the current version of every package in it, sorts everything, and places a comment at the top of the file to show which part it maintains:

# The packages section is generated from the package folders by
# `task manifest`. Edit only the bundles section, then run it again.
schema_version: 2
namespace: skills-yaml
packages:
  skill-creator: "0.1.0"
  skill-reviewer: "0.1.0"
bundles:
  authoring-toolkit:
    packages:
      - skill-creator
      - skill-reviewer

You may notice that the package names now appear twice. The packages section records the exact version of each package, and the bundle then refers to those packages by name, so each version is written down in only one place in the file. Because the command maintains that section, you never have to copy version numbers by hand.

Whenever you publish a new version of a package in the namespace, run task manifest again so that the file picks up the new version. If you forget, task check will fail and tell you that the manifest is out of date.

When you write the bundles section, keep a few rules in mind. Bundle names follow the same rules as skill names. Every skill you list must already be published in the same namespace, and the command refuses to write the file if one of them is not. The members of a bundle are always written out in full, because skm never tries to work them out from the folders it finds. The manifest itself is optional, so a namespace only needs one if it offers bundles.

The workspace namespace works differently. Its manifest is generated by the Workspace packager, together with a few extra fields that record the source repository and the revision its skills came from, so task manifest never changes it.

How people add a bundle

With skm 0.7.0 or later, people can preview a bundle first and then add it to their project:

skm add skills-yaml/authoring-toolkit --source default --kind bundle --dry-run
skm add skills-yaml/authoring-toolkit --source default --kind bundle --yes

The command skm bundle add skills-yaml/authoring-toolkit --source default --yes does the same thing. You can also find published bundles with skm search, which lists each bundle together with the skills it contains.

Adding a bundle writes each of its skills into skills.yaml as a separate entry, pinned to an exact version. From then on, those entries behave like any others, so skm install, skm check and version changes all work as usual. skm does not remember that the entries came from a bundle, which also means that it will not update them automatically if the bundle changes later.
